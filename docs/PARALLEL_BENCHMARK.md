# 并行评测：共享实例的静态只读查询

这条流程回答：同一个字符串索引、相同数据和相同数量的查询，使用更多查询线程后，吞吐量如何变化。它扩展 benchmark 的实验维度，索引算法仍由外部实现提供。

## 运行

在仓库根目录执行，输出目录必须尚不存在：

```bash
python3 -B scripts/benchmark.py \
  --dataset examples/keys.txt \
  --implementation adapters/std_map \
  --implementation adapters/sorted_vector \
  --workload examples/workloads/parallel-read.json \
  --threads 1 2 4 \
  --output results/parallel-read
```

示例每轮 200,000 次查询、10% 未命中、5 轮重复，每轮另外测 1,000 个单线程延迟样本。例子数据很小，用于验证流程；换成自己的真实数据后，应根据查询耗时、波动和机器资源调整操作数。原始键不会被自动截断或抽样。

`--threads` 接受 1–256 的整数，拒绝重复，升序执行；默认 `[1]`。非空负载的线程数不得大于查询总数，非法组合记为 `invalid_input`，其余配置继续。256 是执行器的线程资源边界，不是数据或索引的键数限制。`--jobs` 只控制 CMake 编译并行度；并行查询不要求并行编译。

多个实现、线程数组合依次运行，避免它们同时争抢机器。每个适配包只编译一次，各线程数复用同一可执行程序以及完全相同的 `rows.bin` 和 `queries.bin`。每轮索引重新构建，构建耗时单独记录。

## 实现接入

外部适配器继续使用 `string-index/v1` 的工厂和 `Index` 接口，并用当前头文件重新构建。在返回的描述里显式声明：

```cpp
string_index_bench::v1::Descriptor descriptor() const override {
  string_index_bench::v1::Descriptor result;
  // 填写实现身份、键域和 build/find 能力。
  result.capabilities.concurrent_find = true;
  return result;
}
```

只在实现确实允许多个线程读取同一个已构建实例时设为 `true`。单个 `const find` 仍可能更新缓存或计数器，不能据此推断安全。默认 `false` 保留原有单线程接入；并行组合记为 `unsupported`，不会被 benchmark 自动加锁或复制成多个独立索引。若适配器自身使用锁，须在 `adaptation_notes` 解释，锁的开销进入查询计时。

本次没有并发写入、在线重建或销毁。`descriptor`、`memory_usage` 和析构都在查询线程结束后执行。需要线程注册、专用线程上下文或 epoch 管理的库，目前需在薄适配器中明确完成相应协议；不能仅靠一个布尔声明替代它们。完整承诺见 [实现契约](INDEX_CONTRACT.md#静态并发只读扩展2026-10-17)。

## 固定总工作量与计时

设每轮有 Q 个查询、T 个线程。第 t 个线程接收连续片段，操作数为 `Q // T + (t < Q % T)`，其中 `t` 从 0 开始。所有片段无重叠，恰好覆盖 Q 个查询；每个线程读取同一个实例。例如 Q=10、T=3 时，操作数为 4、3、3。

先创建工作线程并等到全部就绪，再由主线程统一释放。总体 `lookup_ns` 记录从统一释放到所有工作完成的墙钟时间，包含释放、调度和完成同步，排除线程创建、回收、数据准备及索引构建。每个线程单独记录查询耗时、操作数和校验和；查询循环不更新共享计数器。单线程配置直接执行查询循环，不创建额外工作线程。

吞吐量使用 `Q × 1e9 / lookup_ns`，不能把各线程的吞吐量相加替代总墙钟吞吐量。每轮保留原始样本，汇总使用吞吐量中位数，另列最小、最大和总体标准差。

| 指标 | 计算 | 缺失规则 |
| --- | --- | --- |
| 加速比 | 当前线程配置吞吐量中位数 / 同一实现单线程吞吐量中位数 | 未请求 1 线程、基线失败或总操作数不同则不可用 |
| 并行效率 | 加速比 / 线程数 | 加速比不可用则不可用 |
| 逐线程耗时 | 对应线程查询片段的耗时 | 失败组合不产生成功样本 |

效率以比例记录，例如 `0.8` 表示 80%。这套指标采用固定总工作量，反映同一批请求的扩展性。短片段可能主要受唤醒和调度开销影响，增加线程不保证加速；不能据小数据结果宣称实现没有并发能力。

## 校验与延迟

每个配置先执行原有的独立 map 参照校验：空构建、全部键值、全部查询、缺失键和已出现的边界键。并行配置再用同一新建实例按相同划分同步执行完整查询，逐项核对结果；通过后才测吞吐量。工作线程异常会传回主线程，等待所有线程回收，再报告失败并清空测量样本。错误信息保留阶段和位置，不输出键内容。

这可以发现本次并行执行中的错误返回，但不能证明实现对所有可能调度都没有数据竞争。真实索引接入仍需要其维护者确认线程协议，并按需用竞争检测等工具进一步验证。

P50/P99 延迟沿用独立、全新实例上的单线程分散抽样，包含计时器开销。它们不代表多线程负载下的延迟，报告列名与 JSON `latency_mode` 都明确这一点。默认不另设预热轮，未绑核；报告记录 CPU 型号、逻辑 CPU 数以及继承的进程亲和性。

## 输出与复查

| 文件 | 内容 |
| --- | --- |
| `report.md` | 中文结果、测量口径、线程扩展表和边界 |
| `report.json` | 完整数据/负载哈希、配置、执行模式、校验计数、构建身份和原始样本 |
| `summary.csv` | 每个实现、线程数的构建、吞吐、延迟、加速比与效率 |
| `samples.csv` | 带实现和线程数的逐轮吞吐与单线程延迟样本 |
| `scaling.csv` | 可直接绘制扩展性曲线的汇总列 |
| `workers.csv` | 每轮每个工作线程的操作数、查询耗时和校验和 |

构建身份分别保留适配器声明的 `source_identity`、实际源码 checkout 的 `external_source_git.commit` 和已跟踪文件修改状态。Git 不存在、目录未纳入 Git 或命令超时则标为不可用；读取禁用可选索引锁和 fsmonitor，不修改外部 checkout。修改状态只检查 `source_dir` 下已跟踪的文件，不覆盖未跟踪文件或目录外依赖，也不等于递归源码哈希。

新 runner 使用 `string-index-static-run/v2`；总报告使用 `string-index-benchmark-report/v2`。负载 schema 与二进制查询格式不变；Python 仍支持校验历史 v1 runner 的单线程结果。解析器会检查实际线程数、并发能力、完整校验计数、工作线程编号及分配数量，避免把不完整证据当作成功。

不支持、失败、跳过及非法组合都保留状态，性能值留空。退出码 0 仍可能包含 `unsupported`，必须查看实际行状态。线程数不是工作负载 JSON 的字段，因此 uniform/hotspot/Zipf 负载可以与任意合法线程数组合。

## 尚未覆盖

并发写入与混合读写需要操作历史、线性化或其他一致性承诺、线程上下文及内存回收协议，不能直接复用静态答案。扫描、更新、删除、受控 CPU/NUMA 放置、并发负载下尾延迟与更多真实索引适配仍是后续工作。此版本可供同学把已经支持并发读取的模型接入，产出同口径的线程扩展实验。
