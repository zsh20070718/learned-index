# 本周改进记录 · 2026-10-11

本周在中间评测层增加了“访问场景”这条维度：同一份数据、同一批索引，可以直接比较均匀访问、热点访问和 Zipf 偏斜访问。数据来源与索引算法继续由两侧负责，评测层负责把实验条件控制好，并说明结果对应什么条件。

## 为什么做这个

上一版统一入口已经能完成接入、校验、计时和报告，但只能产生均匀随机查询。现实中有些键经常被访问，另一些很少被访问；只测均匀访问，无法观察同一个实现面对不同访问集中程度时的表现。之前旧 TLI 工具虽然有热点和 Zipf 负载，外部适配器却用不上这条完整流程。

这次把访问分布带进统一入口，用户无需转换原始数据，也无需修改索引，就能增加可比较的实验场景。这里提供的是可控的合成访问分布，不能代替真实流量日志。

## 具体改善了什么

| 项目 | 上一版 | 这次 |
| --- | --- | --- |
| 访问场景 | 统一入口只支持均匀随机查询 | 同一个入口支持均匀、热点和 Zipf |
| 控制实验 | 不同工具的负载不容易直接比较 | 三份示例保持查询数、未命中率、种子和轮数一致，只改变访问分布 |
| 解释结果 | 主要记录操作数和未命中数 | 报告同时显示实际访问覆盖和集中程度 |
| 保留历史实验 | 只有 v1 负载格式 | 新能力使用显式 v2；默认入口和 v1 查询序列保留原样 |

### 1. 多一条有实际含义的实验维度

- **均匀访问**：所有源键被等概率抽取，作为对照。
- **热点访问**：默认以 90% 的概率访问前 10% 的源键，其余访问冷区。热区按字节排序定义，实际比例允许随机波动。
- **Zipf 访问**：按排序名次逐渐降低访问概率，默认指数 1.1；指数越大，访问越集中。指数 0 与均匀访问一致。

这些设置改变的是评测层生成的访问序列，所有唯一键仍用于建索引。多个实现继续复用同一份查询，并先校验、后计时。

### 2. 报告能回答“这次到底测了什么”

中文报告展示实际命中数、未命中数、命中访问覆盖的不同键数。热点场景还显示实际热区大小和命中查询落入热区的比例；Zipf 显示命中查询访问第 1 名键的比例。这样能看出配置是否产生了预期的集中访问，而不只是看到一个吞吐量数字。

完整参数和查询哈希保留在 JSON 中，原始样本仍可用 CSV 分析。全部未命中时，热点比例明确写成未测量，避免把缺失键误算成热区成员。

### 3. 旧实验可继续复查，新设置不会静默失效

原有 `static-uniform-point/v1` 格式和默认命令保留；固定旧样例的查询字节哈希作为回归检查。新场景使用 `static-point/v2`，参数按分布校验，比如均匀访问带 Zipf 参数会报错。

热点场景要求至少两个唯一键，单键输入明确说明冷热区无法成立。Zipf 的累计概率表先计入准备内存预算，预算不足时跳过并给出原因，避免悄悄缩小数据规模。

## 怎么使用

在仓库根目录运行，各输出目录必须尚不存在：

```bash
for distribution in uniform hotspot zipf; do
  python3 -B scripts/benchmark.py \
    --dataset examples/keys.txt \
    --implementation adapters/std_map \
    --implementation adapters/sorted_vector \
    --workload "examples/workloads/${distribution}.json" \
    --output "results/access-${distribution}" || break
done
```

分别打开三个目录的 `report.md`，就能对照相同数据和实现下的不同访问场景。每份配置均为每轮 10,000 次查询，其中 1,000 次未命中，重复 3 轮；不需要下载上游代码。换成自己的数据及适配包路径即可继续使用。参数解释见 [统一入口说明](UNIFIED_BENCHMARK.md)。

## 实际怎么验过

- Python 回归检查 **42 项通过**，其中新增 13 项，覆盖旧版字节指纹、Zipf 的均匀极限、冷热区边界、分布频率、独立未命中采样、预算和诊断报告。
- 完整 CTest **6 个测试组全部通过**，其中旧 TLI smoke 的 **60 个案例通过**，原有开发入口继续可用。
- 示例、既有真实词表、既有 MemeTracker URL 三组数据，各跑三种分布和两个现成基线，**18 个组合全部通过**，合计保留 54 轮吞吐量测量和 54,000 个延迟样本。两组真实数据各含 10,000 个唯一键；来源与抽样方式见 [数据集说明](DATASETS.md)。真实数据指键的来源，访问序列仍由评测层合成。
- 独立读取生成的二进制查询，复核键值与成员关系、实际命中/未命中数、集中访问统计、查询哈希和报告样本数。原始输入及两个适配包的文件哈希前后一致；指定已有输出目录会被拒绝，已有报告内容保持不变。
- 独立审查发现并修正了“小预算下，单键热点被误报为预算不足”的问题；复核通过，新增回归保证这种输入在不同预算下都明确报错。

两组真实数据使用相同键数和配置，对排序名次的抽样统计一致。每份负载包含 9,000 次命中、1,000 次未命中：

| 场景 | 命中访问覆盖的不同键数 | 集中程度的实际观测 |
| --- | ---: | --- |
| 均匀 | 5,983 | 从全部 10,000 个源键等概率抽样 |
| 热点 | 1,925 | 89.16% 的命中查询落在 1,000 个热区键上 |
| Zipf（指数 1.1） | 2,022 | 15.53% 的命中查询访问排序第 1 名键 |

这组观测证明三份配置产生了不同的访问集中程度，为后续索引比较提供可控实验条件。它不能直接推出某种分布或索引性能更好。

## 当前边界

这次推进的是静态点查询的实验条件与报告解释。写入、更新、删除、扫描、并发、分片 reader，以及更多真实索引适配仍需后续工作。默认不设预热轮，延迟包含计时器开销，进程未绑核；小规模结果用于验证流程，不据此宣布某个索引全面更快。
