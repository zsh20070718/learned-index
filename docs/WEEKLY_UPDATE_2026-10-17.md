# 本周改进记录 · 2026-10-17

本周把统一 benchmark 从单线程静态查询推进到**共享实例的多线程只读评测、单线程增删改查与扫描混合负载，以及可记录的模型参数对照**，并实际接通两位同学的现有模型适配包。项目继续负责数据、负载、正确性、公平测量和复现，索引算法由同学或外部实现提供。

## 为什么做这次更新

重新核对原始课题材料后，确认多种 workload、访问分布与并发支持都属于整体研究方向。前一周统一入口已具备均匀、热点、Zipf 查询，却不能回答“同一索引增加查询线程后会怎样”。同学各自的模型实验也需要相同的接入和校验条件。

这周先完成并发布并行读取与同学模型接入，再沿同一接口扩展动态操作。已经支持并发读取的实现可做线程扩展；支持修改和扫描的模型可直接测动态维护，所有实现复用相同输入并先独立校验。

| 计时 | 构建、吞吐、独立延迟 | 同步释放已就绪线程，排除线程创建/回收，保留逐线程操作数与耗时 |

每个适配器只编译一次，各线程数使用同一个可执行程序和查询文件。默认仍只测单线程；未声明并发安全的实现不进入并发查询。延迟始终是另建实例的单线程抽样，报告明确标出它不是并发负载下的尾延迟。

静态 runner 先引入 v2 并发证据，再显式升至 v3 记录参数；动态结果使用 `string-index-mixed-run/v1`。原有静态 v1/v2 负载、查询文件格式和默认查询序列保持兼容。报告解析器严格核对线程数、工作量划分与并发校验计数；审查还修复了非法状态字段可能中断整批实验的故障隔离问题。

## 怎么使用

在仓库根目录运行，输出目录必须尚不存在：

```bash
python3 -B scripts/benchmark.py \
  --dataset examples/keys.txt \
  --implementation adapters/std_map \
  --implementation adapters/sorted_vector \
  --workload examples/workloads/parallel-read.json \
  --threads 1 2 4 \
  --output results/parallel-read
```

打开 `report.md` 看结果，再用 `scaling.csv` 对照线程扩展，或用 `workers.csv` 检查各线程是否承担相同口径的工作。`--threads` 控制查询线程，`--jobs` 控制编译任务，含义不同。详细口径见 [并行评测说明](PARALLEL_BENCHMARK.md)。

### 新增五类动态场景

同一命令改用 `--workload examples/workloads/mixed-all.json` 即可评测五种操作；保持单线程，延迟抽样关闭。另有读插、更新删除、带扫描读插和纯扫描配置。初始状态使用按种子选择的真实源键子集，保留其完整排序 rank；后续写入使用记录在元数据中的显式 uint64 值配方。各实现复用同一初始行与二进制操作文件。

独立 map 按序计算答案，对照每次返回值、完整扫描结果、修改后状态与最终键值；校验不进入计时。每轮重建后再播放同一序列，扫描的结果物化与消费计入时间，一次扫描只计一次操作。实际命中、重复插入、更新/删除缺失和扫描返回行数分别记录。完整规则见 [混合评测说明](MIXED_BENCHMARK.md)。

同学已有参数可直接通过 `--parameter block-residual-delta:region_size=512` 和 `--parameter ours-context16:ov_threshold=64` 传入，不必改源码。格式、重复项和实现 ID 在构建前验证，原工厂拒绝未知参数与非法值。

### 小规模实验观察

以下列出全部九种场景中，4 线程相对本实现 1 线程的吞吐量中位数比值：

| 键数据 | 访问分布 | std-map 加速比 | sorted-vector 加速比 |

| 英文词条 | uniform | 1.48× | 1.42× |

| MemeTracker URL | uniform | 2.62× | 2.53× |
| MemeTracker URL | hotspot | 2.17× | 2.30× |
| MemeTracker URL | zipf | 1.91× | 2.11× |

这组结果说明线程扩展不是固定的四倍，数据形态、访问集中程度和调度都会影响观测。它没有绑核、没有专门预热，键数仍较小，不能推导算法排名；单线程与多线程运行都有原始样本可复查，波动见 CSV。

## 混合操作阶段的实际验证

新增主矩阵为 **4 类键数据 × 5 类负载 × 4 个实现 = 80 个组合**：

- 三类真实数据仍各 10,000 个唯一键，初始按配置加载 50% 或 100%；读写场景每轮 20,000 次操作，纯扫描 10,000 次，各重复 3 轮。**42 个通过、18 个明确不支持**，保留 **126 轮吞吐量样本**。
- 另用 13 个字节边界键覆盖空键、NUL、高位字节、前缀关系、600 与 4097 字节长键，并迫使部分插入使用合成新键。每类 200 次操作、重复 2 轮，**14 个通过、6 个明确不支持**，保留 **28 轮样本**。
- 独立 Python 解码器直接读取初始行和操作文件，复算全部结果数量、最终键数、涉及的键数与吞吐量公式，并确认初始值是完整源集合中的 rank。它与 C++ 的逐项参照校验分别检查同一输入。

本轮没有意外失败；不支持项均保留原因及空测量列。完整状态、结果计数、离散程度和输入/程序哈希见 [80 行混合结果 CSV](experiments/mixed-operations-2026-10-17.csv)。实际通过范围如下，三类真实键和字节边界数据均一致：

| 实现 | 读插 | 更新删除 | 带扫描读插 | 完整混合 | 纯扫描 |
| --- | --- | --- | --- | --- | --- |
| std-map | 通过 | 通过 | 通过 | 通过 | 通过 |
| sorted-vector | 不支持写入 | 不支持写入 | 不支持写入 | 不支持写入 | 通过 |
| BlockLearn residual-delta | 通过 | 不支持 update/erase | 通过 | 不支持 update/erase | 通过 |
| 默认 Context16 | 通过 | 通过 | 通过 | 通过 | 通过 |

参数传递还经过两个真实适配包的端到端 CLI 验证。随后在相同英文词条和读插操作序列上，分别测默认值与 `region_size=512`、`ov_threshold=64`，四个配置均通过，见 [参数对照 CSV](experiments/model-parameters-2026-10-17.csv)。这是参数接入与复现证据，不代表这两个取值已经最优。

附加原生检查共 16 个组合：10 个成功运行，4 个正确报告不支持，2 个故意传入非法模型参数并按预期失败、没有成功样本。其中包括两个基线当前程序的 1/2/4 线程静态读取、两个模型带参数的静态查询，以及混合负载拒绝并行请求。

最终 Python 统一入口回归 **65 项通过**，完整 CTest **6 组通过**，继续覆盖旧 TLI 的 **60 个 smoke 案例**。独立审查发现并修复了“重复插入漏计来源”和“混合报告沿用静态并行/延迟说明”两项问题，复核通过；修正前后的原始行和操作文件字节一致。三个真实数据文件、同学模型 checkout 与 TLI/GRE 源码保持不变。

并行阶段与混合阶段的主矩阵合计 **188 个组合：128 个通过，60 个明确不支持**。本周的推进是让现有实现能在更多操作和执行方式下接受同口径评测；未绑核、小数据、合成访问序列的结果仍不用于算法排名。
